# Claude との作り方

最終更新: 2026-09-17

この番組は調査・台本・構図を Claude との会話で作っている。その手順と、
**実際に間違えた箇所**の記録。毎回守る規則のほうは `CLAUDE.md`（Claude Code が
自動で読む）にある。ここは人が読むための文書。

## 分担

**Claude に任せていること**と**任せていないこと**を分けておくのが要点。

| | |
|---|---|
| **任せる** | 一次資料の探索と裏取り／年表・座標の整理／タイル層の実測（叩いて表にする）／写真のライセンス確認／台本の初稿／`shots.py` の構図／踏んだことを docs へ書き戻す |
| **機械に任せる** | 誤読の検出（`readings.py check`）／オウム返しの件数／距離・方角・年数の計算／タイル層が存在するか |
| **人しかできない** | **音を聞く**／**絵を見る**／題材にするかの判断／断定しない線の引き方／名前を決める |

3つ目が実際に効いた。第005回は `suspects` も `scan` も `check` も通したのに、
書き出した動画を聞いた持ち主が誤読を2件拾った。**どちらも scan の出力に
そのまま出ていた。**130行のカタカナを目で追うと、セキ／コクのように
「読みとして成立してしまう」誤りは滑る。

## 回1本の流れ

```
1  町か題材を決める          人。「ここを扱えるか」は素材の有無で決まる
2  調査                      Claude。research.md に年表・座標・出典・実測を書く
3  タイル層を叩く            Claude。使える層を表にする（憶測で書かない）
4  写真を探す                Claude。CC0/PD/CC BY のみ。中身を開いて確認
5  台本                      Claude が初稿 → 人が読んで直す
6  readings check            機械。落ちたら直す
7  scan を読む               Claude が目で追い、**人が声に出す**
8  合成                      tts.py
9  shots.py                  Claude。timeline.json ができてから
10 build check               Claude が1枚ずつ絵を見る
11 本編                      build all
12 通しを見る                **人。音と絵の両方**
13 公開                      compact → gallery release → gallery push
```

**2〜4 と 9 は Claude が速い。7 と 12 は人にしかできない。**

## Claude が実際に間違えたこと（第005回）

書いておかないと同じことをする。

### 読み

`scan` の出力を目で追って「問題なし」と判断したが、2件落ちていた。

| 語 | 誤 | 正 | 見つけた人 |
|---|---|---|---|
| 六百石 | ロッピャッ**セキ** | ロッピャッ**コク**（石高の石） | **人が音を聞いて** |
| 墓所 | **ハカ**ショ | **ボ**ショ | **人が音を聞いて** |
| 向いてる | **ムカイ**テル | **ムイ**テル | 指摘を受けて読み返して |
| ローマ市民権 | ロオマ**シ**・ミンケン | ロオマノ・**シミンケン** | 同上 |

直し方を3通りに分けるのも間違えやすい。**「石」単体を辞書に入れてはいけない**
（石碑・石橋が壊れる。第002回で「碑」をヒで登録して踏んだのと同じ穴）。
石高の語だけを登録し、`guard` に石碑・石橋・墓石を足して `diff` で見張る。

### 事実

- 会話に残っていたメモの「2017年9月に発掘開始」は**第3次**だった。第1次は2014年9月
- 副葬品が出たのは**妻の墓**。本人の墓の副葬品は報告書の抄録に記載が無い
- 父の没年は資料が三通りに割れている → **台本では父の死に触れないことにした**

### 数字

計算せずに書いた初稿が3か所とも違っていた（南→東南東、660m→710m、十九年→十八年）。
**距離・方角・年数は出す。**

### 名前

番組名「まちぶら」が**長崎市の現行事業と衝突**していることに、5本作ってから
気づいた。地域・題材・媒体まで重なっていたので全5本を作り直した。
代案を出すときも、`碑と地形` を提案して**自分が README に書いた
「碑はイシブミと読まれる」を踏んだ。**

### 手が滑る系

- `python tools/build.py ... | tail` にしたせいで `NameError` を見逃した
  （終了コードが `tail` のものになり `set -e` が素通り）
- heredoc に `\n` を書いて実際の改行に潰れ、`clip.py` が構文エラーになった
- 地図ショットと写真ショットは別関数。片方にだけ変数を定義して落ちた

## 出す前に確かめること

公開は取り消しにくいので、**紹介する直前**にまとめて見る。

- [ ] 固有名詞（番組名・題）が既存の事業・番組・商標と衝突しないか
- [ ] 数字と年月日の出どころ。伝聞のままになっていないか
- [ ] 断定していないか。どちらかの側に立っていないか
- [ ] 写真とBGMのライセンス（SA・NC が混じっていないか）と、クレジットが**絵に出ているか**
- [ ] 立ち絵が入っていないか
- [ ] 音を通しで聞いたか。**絵を通しで見たか**
- [ ] 公開リポジトリに配ってはいけないものが入っていないか

## Claude に渡すと速いもの

この回で実際に効いた依頼のかたち。

- **「憶測で書かずに叩いて確かめて」** — タイル層の整備範囲、写真のライセンス、
  読み。表にして `research.md` に残る
- **「clone して第一話から始められるか試して」** — 机上では分からない障壁が出た
  （雛形が無い／生の traceback／フォントが Windows 固定）
- **「この名前、衝突を調べて」** — 5本作ってから気づく事故を防げる
- **「踏んだことを README に書き戻して」** — 同じ穴を掘らなくなる。
  README の「つまずきどころ」はこの積み上げ

逆に、**「いい感じにして」は効かない。**何を芯にするか、どこで断定を避けるかは
人が決める。決めたことを `episode.json` の `mood` と `research.md` の
「扱い方の方針」に書いておくと、次の会話でも同じ線を引ける。
