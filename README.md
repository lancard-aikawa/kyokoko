# 今日はここに

〒や町名を指定すると、その町の遺構・歴史建造物・地名の由来にまつわる「碑」の話を集め、
読み上げシナリオを作り、VOICEVOX と地図で動画にする。参考番組: ブラタモリ。

回には**テーマ**（何を扱うか）と**形式**（どう見せるか）がある。
別の軸なので掛け合わせる。詳しくは `docs/format.md`。

- テーマ — 石碑 / 土木 / 地形 / 史跡。町を指定すると、素材の有無で作れるものが決まる
- 形式 — 対話 / クエスチョン

## 新しい回を作る

```
python tools/new.py 006 isahaya-ikiriki "諫早市 多良見町伊木力"
```

`episodes/006-isahaya-ikiriki/` に `episode.json` / `script.md` / `shots.py` /
`photos.json` の雛形ができる。町の中心は国土地理院の住所検索から入る
（引けないときは `--center 32.7476,129.8686`）。

**雛形はそのまま通る。**作った直後に合成とビルドを走らせると 40 秒ほどの
動画ができるので、まず一周させて環境が揃っているか確かめられる。
そのあと中身を自分の町の話に差し替える。

**自分の第一話から始めたいとき**は、`episodes/` の既存の回を消してから
`python tools/new.py 001 <slug> "<町名>"` と打つ。番号は打った値がそのまま
使われるので、設定ファイルは無い。

各ファイルの書式は **`docs/episode-files.md`**。

## 作る手順

1. **VOICEVOX エンジンを起動**

   ```
   "%LOCALAPPDATA%\Programs\VOICEVOX\vv-engine\run.exe" --host 127.0.0.1 --port 50021
   ```

2. **回を作って、調べて `research.md` と `script.md` を書く**

   ```
   python tools/new.py 006 isahaya-ikiriki "諫早市 多良見町伊木力"
   ```

   雛形ができる（上の「新しい回を作る」）。調査と台本は Claude との会話で。
   書式は `docs/episode-files.md`、**Claude との分担と注意は `docs/claude.md`**。

3. **配役が引けるか見る**（環境を移したときだけ）

   ```
   python tools/tts.py --speakers episodes/00N-...   配役とエンジンの話者一覧
   ```

4. **読みを確かめる**

   ```
   python tools/readings.py check <ep> 合成の前に機械で止める（誤読があれば落ちる）
   python tools/readings.py diff      補正の前後で何が変わるかを見る
   python tools/readings.py phrases "<台詞>"   アクセント句と核の位置
   ```

5. **合成**

   ```
   python tools/tts.py episodes/00N-...
   ```

6. **構図を確かめる**

   ```
   python tools/build.py --ep episodes/00N-... check
   ```

7. **動画にする**

   ```
   python tools/build.py all          全話 + 通し（立ち絵なし）
   python tools/build.py 2 3          一部だけ作り直す
   python tools/build.py remux        音声だけ差し替える（絵が変わっていないとき）
   python tools/build.py all --chara  立ち絵を入れる
   ```

   **速くする手が2つある。**

   ```
   python tools/build.py all --jobs auto   ショットを同時に描く（コア数の半分、最大4）
   python tools/build.py all --ff          絵づくりを ffmpeg のフィルタに任せる
   ```

   `--jobs` はショットが互いに関係ないことを使う。`--ff` はカメラワークが
   「静止画の上をパン・ズームするだけ」であることを使う。ログの
   `[ffmpeg]` / `[PIL: 理由]` でどちらが描いたか分かる。

   **この2つは足し算にならない。**同じコアを取り合うので、両方付けると
   かえって遅い。16コアで第005回（本編 10分19秒）を通しで作った実測:

   |  | `--jobs 1` | `--jobs 4` |
   |---|---|---|
   | 既定（PIL） | 24分42秒 | **11分56秒** |
   | `--ff` | 17分00秒 | 13分53秒 |

   コアがあるなら `--jobs auto` だけでよい。`--ff` が効くのはコアが少ない
   機械と、1ショットだけ描き直すとき。

   **既定は `--jobs 1` のまま置いてある。**速さのためではなく、初回は地理院
   のタイルを取りに行くため。同時に描くとリクエストが人数ぶん増える。
   タイルが溜まったあと（＝2回目以降）に付けるのが行儀がよい。

8. **YouTube に上げる材料を出す**（公開するとき）

   ```
   python tools/gallery.py youtube --ep episodes/00N-...
   ```

   `dist/` に、そのまま貼れる形で書き出す。

   ```
   dist/youtube-title.txt         タイトル
   dist/youtube-description.txt   概要欄（紹介＋チャプター＋クレジット＋リンク）
   ```

   概要欄の頭に置く2〜3行は `episode.json` の `summary` から取る。**1行1文で
   書く**（YouTube は改行をそのまま出すので、文の途中で折ると行が割れて見える）。

   再生リストのタイトルと説明は回にひもづかないので、別に出す。

   ```
   python tools/gallery.py playlist     -> dist/youtube-playlist-*.txt
   ```

   公開ずみの回（`episode.json` の `youtube` が入っている回）だけを番号順に
   並べる。回が増えたら作り直す。

   **上げるのは `dist/<回>.mp4`。`-web` は上げない**（YouTube 側で再圧縮されるので
   二重圧縮になる。あれは Releases で直接配るためのもの）。
   字幕は `dist/<回>.srt` に書かれる。**絵には焼き込み済みなので映像には要らないが、
   SRT を付けると YouTube の中で検索に乗り、自動翻訳も効く**（焼き込みの文字は
   画像なので1文字も引っかからない）。視聴者が字幕を ON にすると二重に出るので、
   上げるかは選ぶ。

9. **公開用に軽くする**（ファイルそのものを配るとき）

   ```
   python tools/build.py --ep episodes/00N-... compact          H.264 / 約半分
   python tools/build.py --ep episodes/00N-... compact --hevc   H.265 / 約1/3
   ```

   dist/ の通しは高画質のまま残り、隣に `-web` / `-hevc` の複製ができる。
   **YouTube に上げるだけなら要らない。** 向こうで再圧縮されるので、
   先に削っておくと二重圧縮になるだけ。

## つまずきどころ

この番組を作る過程で実際に踏んだもの。同じ穴を掘らないための覚え書き。

**アクセントは `accent` を書き換えただけでは音に出ない。**
合成が見ているのはモーラごとの `pitch` で、`accent` はただの印。書き換えたあと
`/mora_data` で計算し直さないと、画面上は核が動いて見えるのに音は一切変わらない。
`tts.SYNTH_VERSION` を上げると全行を録り直せる。

**ffmpeg の concat + outpoint は無音を正確に切れない。**
`-c copy` ではパケット境界でしか切れず、1 箇所あたり 0.05〜0.08 秒ずつ伸びる。
無音が 28 箇所あると 1.4 秒ずれて、字幕が後半ほど音声から遅れる。
いまはサンプル単位で自分で組み立てている（`tts.concat_wav`）。

**読み辞書を直したら録り直しが要る。**
台詞も設定も変えていないので、判定に辞書の指紋を混ぜないと古い音声が残る。

**語単位の辞書は複合語を巻き添えにする。**
「碑」を ヒ に直したら「石碑」が イシヒ になった。`readings.py diff` が
`guard` 語の読みを補正前後で比べて教えてくれる。1 か所だけ直したいときは
script.md に `碑《ひ》` と書く（ルビ）。

**ルビの範囲は漢字・カタカナの連なりだけに限る。**
`[^《》]+?` のように書くと直前の地の文まで飲み込み、「この碑《ひ》って」が
「ひって」になる。読み文が字幕文より極端に短くなったら止まるようにしてある。

**地理院タイルはレイヤごとに範囲が違う。**
`ort_USA10`（1945〜50年の米軍撮影）は全国をカバーしておらず、長崎は 404 だった。
シナリオに年代を書く前にタイルの存在を確かめること。

**重ねる層の透明を黒にしない。**
`swale`（明治期の低湿地）は塗った所以外が透明の層で、`clip.Master` が RGB に
潰していたため透明が黒になり、`alpha` で重ねると陸が黒く沈んでいた。第006回の
`check` で、明治の海を重ねた町が真っ黒に出て気づいた。いまは透明を持つ層だけ
RGBA のまま持ち、タイルの透明に層の `alpha` を掛けて重ねる（PIL 版のみ。
`--ff` はこれまでどおり RGB）。**過去の回を描き直すと、swale を使ったショットの
見た目が変わる。**

**並列で描くとタイルのキャッシュが取り合いになる。**
`--jobs` で同じタイルを2つのプロセスが取りに行くと、Windows では相手が開いている
ファイルへの置き換えが `PermissionError`（アクセス拒否）で落ちる。先に置かれた
タイルがあればそれを使うようにした（`tiles.fetch_tile`）。

**画像はファイル名を信じない。**
`Nagasaki-Dejima-1770.jpg` は 1770 年の絵図ではなく、現代の復元建物の写真だった
（数字はカメラの連番）。必ず開いて中身を見る。

**回をまたぐものと、回に属するものを分ける。**
BGM と読み辞書は番組のもので、回ごとではない（`assets/bgm/`, `tools/readings.json`）。
写真とシナリオと構図は回のもの（`episodes/*/`）。1 回目だけを作っている間はこの
区別が要らないので、2 回目で初めて破綻する。話数も通しのファイル名も同じで、
直書きすると次の回で詰まる。`episode.json` の chapters と回のフォルダ名から引く。

**読みは合成の前に総ざらいする。しかも2通りで。**
`python tools/readings.py suspects <ep_dir>` は台詞中の漢字語を全部さらう。
第002回では 208 語のうち 8 つが誤読だった（思案橋→シアンキョウ、袋橋→
フクロキョウ、桃渓橋→モモ・ケエキョウ、風頭山→カザガシラサン ほか）。
眼鏡橋が正しく読めていたので、他の橋も大丈夫だと思い込むところだった。

それでも足りない。**語を単独で読ませると、文脈で決まる読みは拾えない。**
`scan <ep_dir>` は台詞を 1 行ずつ丸ごと読ませて文章と並べて出す。これで
アーチ橋→アアチキョオ、同じ人→ドオジジン、降りました→オリマシタ が出た。
どれも語だけ見れば正しい読みになっていた。逆に、断片を切り出して読ませる
やり方は誤読を「作る」だけで役に立たない（「烈な雨が降」→クダ）。

**単漢字は、熟語になっていないと片方の読みに倒れる。**
第005回で「表には」がヒョウニワ、「いちばん上に」がイチバンジョウ、
「刷られた」がズラレタ、「空くんですか」がスクンデスカ になった。
どれも熟語（表側・丘の上・印刷）なら正しく読める。`readings.py` の
`TRAPS` に足してあるので `check` が止める。

**`scan` を目で追っても落ちる。最後は耳で聞くこと。**
第005回は `suspects` も `scan` も通したのに、書き出した動画を聞いた持ち主が
2件拾った。「六百石」がロッピャッセキ（石高の石は こく）、「墓所」がハカショ。
どちらも scan の出力に**そのまま出ていた**のに、130行の読みを目で流していて
気づかなかった。**カタカナの列は読み飛ばせてしまう。**
数を数える語（石・貫・俵）と、墓・寺の用語は音読み・訓読みが割れやすいので、
そこだけでも声に出して確かめる。
そのとき「向いてる」→ムカイテル と「ローマ市民権」→ロオマシ・ミンケン も
見つかった。前者は `TRAPS` に足した（`向《む》いてる` と書けば通る）。
後者はカタカナの地名が「市」を吸うので、**助詞を1つ入れて切る**
（ローマの市民権）。こちらは誤検知なしの規則が書けなかったので機械化していない。

**一度直した誤読を、次の回でまた出す。**
「〜の方」と「雨が降りました」は、第002回で直したのに第004回でまた素の漢字で
書いて同じ誤読を出した。どちらの読みも正しい語なので辞書では直せず、書く側が
気をつけるしかない。**気をつけるのは無理なので機械で止める。**
`python tools/readings.py check <ep_dir>` を合成の前に通す。

**VOICEVOX の話者番号は、エンジンの版で変わりうる。**
`episode.json` に `speaker: 8` と直書きすると、別の環境で**別のキャラが喋る**。
いまは `label`（「春日部つむぎ / ノーマル」）を正として、合成のたびに
`/speakers` から番号を引き直す。食い違っていたら警告を出して、引けたほうを使う。
`python tools/tts.py --speakers <ep_dir>` で確かめられる。

**探訪役の返しが1種類に偏るとオウム返しに聞こえる。**
「直前の台詞から語を借りて体言止め」が第001・002回で8件ずつあった。
1回なら驚き、5回並ぶと相槌マシン。`check` が件数を出す。詳しくは docs/format.md。

**読みが割れる単漢字は、辞書ではなくひらがなに開く。**
「方」は のほう とも のかた とも読む。どちらも正しいので、辞書に入れると
必ず片方を壊す。前後を含めて「日本の方」で登録しても、その並びしか直らない。
script.md 側で「日本のかた」と書く。放送の表記でもかな書きが標準なので
字幕も自然になる。同じ扱いの語: 方・他・間。

**品詞がぶつかると priority 10 でも負ける。**
「日本人」は 日本→ニホン を登録しても直らず、固有名詞で登録しても
ニッポンジン のままだった。普通名詞（`COMMON_NOUN`）にすると通る。
readings.json の `type` で語ごとに切り替える。

**碑を扱う回は、まず地理院の自然災害伝承碑データを見る。**
全国684市区町村 2,469 基（2026-08-27 時点）が **碑文つき・座標つき** で
1 ファイルにまとまっている。**基数は増えるので数を引くときは本家を見ること。**
`curl -sL -o x.zip https://www.gsi.go.jp/common/000250768.zip`

**構文が通っても動くとは限らない。**
パッチを当てたあと `ast.parse` だけ見て通したつもりになり、未定義の関数を
呼んでビルドが落ちた。直したら実際に呼ぶこと。

**写真の寄りは、ショットから必要な余裕を計算する。**
`render_photo_shot` は元画像を「画面を覆う倍率 × 1.25」で先に拡大していた。
`kb` にそれを超える拡大率を書くと crop が画像からはみ出し、**PIL が黒で埋める**。
例外も警告も出ないので、書き出した動画を見るまで気づけない。いまは `kb` の
最大値から余裕を決めている。

**ズームは主役の大きさから決める。**
z12 は画面 1920px で横 62km になる。7km の堤防を z12 で撮ろうとして、
線が読めなかった。z13=31km、z14=15km、z15=7.7km。camera の scale はここに掛かる。

**古い空中写真は陸しか撮っていないことがある。**
1974年の `gazo1` は諫早湾の上が真っ黒だった（27%が欠測）。海を見せる回では使えない。
1961年の `ort_old10` は湾まで写っていて、引き潮の干潟が広がる。

**`LAYERS` のズーム範囲は、メモではなく描画の指示。**
`clip.Master` は要求ズームをこの範囲へ**切り上げて**タイルを取りに行く。
下限を実際より高く書くと、広い画角のショットが高いズームに繰り上がり、
その層が持っていない範囲を掴んで**欠測が真っ黒に出る**。第004回で
シームレス写真を (14,18) と書いていたせいで、z12 の俯瞰が z14 になり
画面の半分が黒くなった。実測は z5 でも 0%。範囲は測って書くこと。

**空中写真は年代ごとに整備範囲が違う。**
長崎県で実測したところ 1961〜69年・1974〜78年・現在はどこでも揃い、
1945〜50年は市街地だけ、1984〜86年は全滅だった。山岳部は現在のオルソが無い。

**最新のオルソには撮影時期の継ぎ目が入る。**
シームレス空中写真でも同じ（元画像が同じなので）。継ぎ目の緯度を測って、
カメラの中心をずらして画面の端へ逃がす。

**タイトルとラベルは同じところに出る。**
番組名は画面の中央に、地図のラベルもカメラの中心付近に出るので、同じ瞬間に
両方を描くと番組名の上に町名が重なる。第001〜003回の5枚が
「今日はこ眼鏡橋こに」になっていた。ショットを割って逃げることもできるが、
ラベルには終了時刻が無いので毎回割ることになる。いまは `clip.title_active` が
**タイトルが出ている間だけラベルと注記を伏せる**。どの回でも自動で効く。

**傾斜量図は、人工の段差が無いところでは何も出ない。**
城跡の堀や古墳には効くが、ただの丘陵では陸が真っ白につぶれるだけだった。
陰影起伏図に替えるか、淡色地図のまま置く。
**裏を返すと、段だらけの土地では強い。**第005回の伊木力はみかんの段々畑なので、
z15 で段が面にびっしり出た。谷を横切るダムの堤体も黒い一本の線になる。
「人工の段差があるか」で決めること。畑も人工の段差である。

**`LAYERS` のズーム上限を超えると、黙って引き伸ばされる。**
`clip.Master` は `src_zoom = max(lo, min(zoom, hi))` なので、下限は切り上げ、
上限は**切り下げてから拡大**する。欠測のような分かりやすい壊れ方をせず、
ただ眠い絵になるので気づきにくい。傾斜量図 `slopemap` は上限 15、
色別標高図 `relief` も 15。この2つは z16 以上のショットに置かないこと。

**地名の読みは日本郵便の郵便番号一覧で確かめられる。**
カタカナのふりがなが付いている。第005回の「山川内」は VOICEVOX が
ヤマカワナイ と読んだが、正しくは **やまがわうち**（タラミチョウヤマガワウチ）
だった。Wikipedia にも地図にも読みは無い。町名・大字はここで引くのが早い。

**画質を落とすより先に、何が重いのかを見る。**
地図と写真の動画は CRF 19 で 1080p30 なら 7〜12 Mbps 出る。細かいのは地図の
文字だけで、そこは CRF を落としても崩れない（CRF 23 で 5px の町名が読めた。
SSIM 0.989、サイズは 46%減）。音声はモノラル 24kHz の 98kbps しかなく、
全体の 1.3% なので触っても意味がない。つまり削るところは動画の CRF だけ。

**YouTube に上げるなら縮めない。**
向こうが再圧縮するので、先に削ると二重圧縮になる。1080p30 の推奨は 8 Mbps で、
CRF 19 の出力はもともとその範囲に入っている。compact はファイルを直接配るとき用。

**VOICEVOX は音声と立ち絵で規約が別物。**
音声が法人フリーでも、立ち絵は法人要許諾のキャラが多い。とくに
「このプログラムでこんな動画が作れます」と見せる用途は宣伝手段にあたり、
ほぼ確実に許諾が要る。だから立ち絵は既定では出さない。
詳しくは `docs/character-art-license.md`。

**BGM を敷いた音声は、同じ入力でもビット単位では再現しない。**
`mix.mix` を3回続けて走らせると、1回目と2〜3回目で md5 が変わる。長さも
サンプル数も同じで、違うのは末尾のフェードアウトのあたりだけ。BGM を
`-stream_loop -1` で繰り返しているので、繰り返しの継ぎ目がサンプル単位で
きっちり揃わないためらしい。聞いて分かる差ではない。**映像が変わったかを
見たいときは、mp4 全体の md5 ではなく映像ストリームだけを比べること。**

```
ffmpeg -v error -i a.mp4 -map 0:v -c copy -f md5 -
```

**速くしたいとき、グラフィックボードは効かない。**
遅いのは絵の合成で、それをやっているのは PIL（CPU）と x264（CPU）。内訳は
実測で **PIL の合成が 68%、x264 が 32%**。GPU に渡せる仕事がほとんど無い。
効く手は2つで、どちらも CPU の使い方の話:

- `--jobs`  ショットは互いに関係ないので、まとめて別のプロセスに配る。
  ただし **頭打ちが早い**。16コアでも 2倍強（24分42秒 -> 11分56秒）で、
  3本目から先はほとんど伸びない。コアではなくメモリ帯域が天井。
- `--ff`  カメラワークは「静止画の上をパン・ズームするだけ」なので、
  そこは ffmpeg のフィルタの仕事にできる。文字だけ PIL に残す
  （見た目を1ピクセルも変えないため）。単独なら 1.45倍。

**そして2つは足し算にならない。**`--ff` は ffmpeg 自身が全コアを使うので、
それを4本同時に走らせると取り合いになる。実測では `--jobs 4` だけの方が
`--jobs 4 --ff` より速い（11分56秒 対 13分53秒）。表は「作る手順」の 7。

`--jobs` は **映像ストリームがビット単位で同じ**（`-map 0:v -c copy -f md5`
が一致する）。`--ff` は拡大の補間器が違う（PIL は LANCZOS、ffmpeg は
swscale）ぶんだけ画素が動くが、並べても見分けはつかない。詳しくは
`tools/clip_ff.py` の冒頭（ffmpeg で踏んだ罠が6つ書いてある）。
